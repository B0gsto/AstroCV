Swapping the OCR engine under a production pipeline is not something to do on a hunch. Before moving from Azure Document Intelligence to Mistral OCR, I ran both against the same documents and measured the things my pipeline actually depends on.

## Why benchmark at all

Vendor benchmarks are run on clean, public datasets. My documents are scanned contracts and supplier invoices: stamped, skewed, photographed on a counter. The only benchmark that predicts how an engine behaves on my data is one run on my data.

## The test set

- **[N] documents**, sampled from real traffic rather than hand-picked.
- A deliberate mix: [X] clean digital PDFs, [Y] flatbed scans, [Z] phone photos.
- [LANGUAGES] represented in proportion to production.
- Ground truth labelled by hand for the fields the pipeline needs: [FIELD LIST].

Sampling matters more than size. A small set that looks like production beats a large one that doesn't.

## What I measured

1. **Field-level accuracy.** Did the pipeline end up with the right value for each field? This is the number the business feels. Normalise before comparing (dates, decimal separators, whitespace), otherwise formatting noise is counted as errors.
2. **Character error rate** on the raw text, to separate "OCR misread it" from "extraction picked the wrong thing".
3. **Latency** per page, at the median and at p95. The tail is what queues feel.
4. **Cost per page** at production volume.
5. **Layout output.** Does the engine return coordinates good enough to [highlight the source on the PDF](/blog/highlighting-pdfs-with-bounding-boxes)?
